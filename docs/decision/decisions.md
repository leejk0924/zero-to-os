# 결정 기록

프로젝트 전체에 걸친 결정과 그 이유를 적는다. 한 단계에만 해당하는 선택은 그 단계의 설계 문서(`specs/`)에 있다.

결정을 바꿀 때는 줄을 지우지 않고, 바뀐 날짜와 이유를 덧붙인다.

## 기반

| 번호 | 결정 | 이유 | 버린 대안 | 날짜 |
|---|---|---|---|---|
| D1 | 언어는 Rust stable | 사용자가 정함. nightly 전용 기능에 기대지 않아 빌드가 깨질 일이 적다 | nightly (커널 안 테스트 프레임워크를 쓸 수 있음) | 2026-11-14 |
| D2 | CPU는 RISC-V 64, QEMU `virt` 머신 | 개방형 표준이라 라이선스 제약이 없고 실제로 활용할 곳이 많다. 부팅이 단순해 OS 개념에 시간을 쓸 수 있다 | x86_64 (자료가 많지만 16→32→64비트 전환 등 호환성 유산이 많음), AArch64 | 2026-11-14 |
| D3 | 펌웨어 없이 M 모드부터 직접 작성 (`-bios none`) | 전원 직후 실행되는 모든 명령어가 이 저장소의 코드가 된다 | OpenSBI 위에서 S 모드부터 (실제 보드와 같지만 M 모드가 가려짐) | 2026-11-14 |
| D4 | 모놀리식 커널 | 최종 목표까지 가는 길이 가장 짧고 Linux와 구조가 같다 | 마이크로커널 (나중에 바꾸려면 트랩·시스템 콜·스케줄러를 다시 짜야 함. 범위 밖으로 둠) | 2026-11-19 |
| D5 | 구조와 순서는 xv6-riscv를 기준으로, 의미 있게 다른 곳은 Linux 방식 | 막혔을 때 비교할 기준이 있고, 배운 것이 실무(Linux)로 이어진다 | 독자 설계 | 2026-11-19 |

## 동시성

| 번호 | 결정 | 이유 | 버린 대안 | 날짜 |
|---|---|---|---|---|
| D6 | 1단계부터 코어 4개(`-smp 4`), 스핀락과 코어별 상태를 처음부터 전제 | 사용자에게 동시성은 필수 주제다. 나중에 넣으면 공유 자료구조를 모두 다시 손봐야 한다 | 한동안 코어 1개 (디버깅은 쉬움) | 2026-11-19 |
| D7 | 스케줄러는 전역 실행 큐 + 락 라운드 로빈으로 시작, 경합을 측정한 뒤 코어별 실행 큐로 | 단순한 구조의 한계를 직접 측정하고 나서 바꿔야 왜 필요한지 안다 | 처음부터 코어별 실행 큐 | 2026-11-19 |
| D8 | 최종 목표 달성 전에는 사용자 스레드를 만들지 않음 | 에코 서버는 스레드 하나와 `epoll`로 충분하다. 동시성은 커널 쪽에서 다룬다 | `CLONE_VM`, `futex` 구현 | 2026-11-19 |
| D22 | 지원 코어는 최대 4개(`-smp 4`에 맞춤). 번호가 4 이상인 코어는 `_start`에서 `wfi`로 멈춘다 | 부트 스택을 코어 수만큼 미리 잡아야 하므로 상한이 필요하다. 그 이상 코어가 들어오면 남의 메모리를 스택으로 쓴다 | 코어 수를 런타임에 알아내 스택을 나누기(장치 트리 해석이 필요하다) | 2026-11-21 |
| D23 | 커널 코드(S 모드)는 코어 번호를 `tp` 레지스터에서 읽는다(`hartid()`). `tp`를 다른 용도로 쓰지 않는다 | S 모드에서는 `mhartid`를 읽을 수 없다. `tp`는 컴파일러가 쓰지 않는 레지스터다. xv6와 같다 | 코어 번호를 메모리에 두기(어느 칸이 자기 것인지 알려면 다시 코어 번호가 필요하다) | 2026-11-21 |
| D24 | 패닉은 처음 패닉한 코어만 출력한다. UART 락을 정해진 횟수만 `try_lock`으로 시도해 얻으면 놓지 않고, 못 얻으면 락 없이 출력한다 | 락을 쥔 채 패닉해도 메시지가 나와야 하고, 다른 코어의 출력과 섞이면 안 된다. Linux `panic_cpu`, `printk`의 패닉 때 콘솔 락 처리와 같은 발상이다(ADR 0002, 0003) | 패닉도 `lock()`으로 출력(락을 쥔 채 패닉하면 메시지가 안 나온다), 락 없이 바로 출력(다른 코어 출력과 섞인다) | 2026-11-21 |

## Linux와 맞추는 것

| 번호 | 결정 | 이유 | 버린 대안 | 날짜 |
|---|---|---|---|---|
| D9 | 시스템 콜은 Linux RISC-V 규약의 번호와 의미를 따르고, 필요한 것만 하나씩 구현 | 개념이 Linux 매뉴얼(`man 2`)과 1:1로 대응한다 | 독자 규약 | 2026-11-19 |
| D10 | 가상 메모리 단계에서 커널을 상위 절반 주소로 옮김. 그전에는 물리 주소 `0x80000000` | 모든 프로세스가 커널 영역을 공유해 시스템 콜 때 페이지 테이블을 바꾸지 않는다. Linux와 같다 | xv6 방식 (커널·사용자 페이지 테이블 분리, 트램펄린 필요) | 2026-11-19 |
| D11 | 프로세스는 `clone`(fork 용도) + `execve`. 전체 복사를 먼저 만들고 copy-on-write로 개선 | Linux 규약과 맞고, 두 방식을 비교해 볼 수 있다 | `spawn` 방식 | 2026-11-19 |
| D12 | 파일 시스템은 ext2 일부 호환(저널링 없음) | Mac의 `mke2fs`로 이미지를 만들고 `e2fsck`로 커널이 쓴 결과를 검사할 수 있다. `brew install e2fsprogs` 필요 | xv6 방식 직접 설계 (로그가 있지만 검사 도구를 직접 만들어야 함) | 2026-11-19 |
| D13 | 멀티플렉싱은 `ppoll` 먼저, 그다음 `epoll`(레벨 트리거, `epoll_pwait`) | Linux RISC-V 규약에는 `poll`, `epoll_wait`가 없다. 둘 다 만들어야 `epoll`이 왜 필요한지 측정할 수 있다 | `epoll`만 구현 | 2026-11-19 |
| D14 | 사용자 프로그램은 직접 만든 작은 Rust 라이브러리(시스템 콜 래퍼, `print!`)로 작성 | C 크로스 툴체인과 폭넓은 시스템 콜 구현이 필요 없다 | `musl` 포팅 | 2026-11-19 |

## 크레이트와 테스트

| 번호 | 결정 | 이유 | 버린 대안 | 날짜 |
|---|---|---|---|---|
| D15 | 크레이트 정책: 1~3단계(부팅, 트랩, 메모리)는 직접 구현. 크기가 크고 현재 단계에서 먼 부분만 크레이트를 쓰고, 우리가 정의한 인터페이스 뒤에 숨긴다 | 작은 부분은 크레이트가 배울 대상 자체를 가린다. 인터페이스 뒤에 두면 나중에 직접 구현으로 바꿀 수 있다 | 전부 직접 구현, 전부 크레이트 | 2026-11-19 |
| D16 | 네트워크 스택은 `smoltcp`로 시작하고 자체 `NetStack` 인터페이스 뒤에 둠. 인터페이스는 크레이트 API를 옮기지 않고 우리 필요에 맞춰 설계 | TCP/IP를 직접 만들면 최종 목표가 크게 멀어진다. 소켓과 멀티플렉싱에 먼저 집중한다 | 직접 만든 TCP/IP 스택 (범위 밖으로 둠) | 2026-11-19 |
| D17 | 커널은 QEMU 출력 검사로, 하드웨어와 무관한 로직은 별도 크레이트로 분리해 Mac에서 `cargo test`로 확인 (2단계부터 분리) | stable에서 가능한 방식이고, 로직 테스트가 빠르다 | 커널 안 테스트 프레임워크 (nightly 필요) | 2026-11-19 |

## 진행 방식

| 번호 | 결정 | 이유 | 버린 대안 | 날짜 |
|---|---|---|---|---|
| D18 | 코드는 에이전트가 작성하고, 학습 내용은 옵시디언 `zero-to-os/` 노트로 정리 | 사용자가 정함. 노트로 남겨 두고 읽으며 학습한다 | 대화로 설명, 사용자가 직접 작성 | 2026-11-19 |
| D19 | 태스크마다 새 서브에이전트가 구현하고 Codex가 검토 | 사용자가 정함. 구현한 쪽과 다른 모델이 검토한다 | 한 세션에서 직접 구현 | 2026-11-19 |
| D20 | 지시와 결정은 프로젝트 문서로 관리 (`AGENTS.md`, `docs/`) | 사용자가 정함 | 대화로만 지시 | 2026-11-19 |
| D21 | 이슈 하나(단계)에 PR 여러 개(태스크마다 하나)를 `gh stack`으로 쌓는다. 커밋·브랜치 규칙은 `docs/git-convention.md` | 사용자가 정함. PR을 최소한의 기능 단위로 작게 유지해 이해하기 쉽게 한다 | 단계 하나를 브랜치·PR 하나로 (`stage-1-boot`) | 2026-11-19 |
