# 2단계 설계: 트랩 → 타이머 인터럽트 → 코어마다 틱 출력

- 작성일: 2026-11-19
- 이슈: #2
- 프로젝트 전체의 결정과 이유는 `docs/decision/decisions.md`에 있다. 이 문서는 2단계에만 해당하는 내용을 다룬다.
- `docs/decision/qna.md`의 Q21(타이머 경로), Q22(스핀락을 분리 크레이트로 옮길지)는 아직 답을 기다린다. 이 문서는 두 질문의 추천안을 기준으로 썼고, 답이 다르면 해당 절을 고친다.

## 의도

CPU가 하던 일을 멈추고 커널로 뛰어드는 길(트랩)을 직접 만든다. 예외(명령어가 일으킨 문제)와 인터럽트(바깥에서 온 신호)가 같은 입구로 들어와 어떻게 갈라지는지, 처리한 뒤 어떻게 하던 일로 정확히 돌아가는지를 본다.

동시성 쪽에서는 1단계의 스핀락이 인터럽트 앞에서 깨지는 경우를 겪는다. 락을 쥔 코어에 인터럽트가 들어와 처리기가 같은 락을 잡으려 하면 그 코어는 영원히 멈춘다. 백엔드로 치면 같은 스레드가 재진입 불가능한 뮤텍스를 두 번 잡는 상황이다. 이것을 실험으로 보고, 락이 인터럽트를 끄도록 고친다.

이번 단계부터 하드웨어와 무관한 로직을 별도 크레이트로 떼어 Mac에서 `cargo test`로 확인한다(D17).

## 목표

- `cargo run`을 하면 코어 4개가 각자 주기적으로 `[S] hart N 틱 K`를 출력한다. 줄은 섞이지 않는다.
- 커널 안에서 예외가 나면 조용히 멈추지 않고 원인(`scause`), 위치(`sepc`), 부가 정보(`stval`)를 출력하며 패닉한다.
- `ebreak` 예외는 처리한 뒤 다음 명령어로 돌아가 실행을 계속한다. 예외에서 "돌아가는" 길도 동작함을 보인다.
- 인터럽트 처리기에서 `println!`을 써도 교착되지 않는다.
- `cargo test`(Mac 호스트)로 분리 크레이트의 테스트가 통과한다.

## 이번 단계에서 하지 않는 것

- 사용자 모드(U 모드)에서 오는 트랩, 시스템 콜 (5단계)
- 문맥 교환, 선점형 스케줄링. 타이머는 틱을 세고 출력만 한다 (5단계)
- 외부 인터럽트(PLIC), UART 입력
- 코어 간 인터럽트(IPI, 소프트웨어 인터럽트)
- 디바이스 트리 해석. 타이머 주파수는 상수로 둔다
- 부동소수점 레지스터 저장. 커널은 부동소수점을 쓰지 않는다
- 벽시계 시간, 틱 없는 커널(tickless)

## 피해야 할 것

- 동작은 하지만 사용자가 이해하지 못한 코드가 쌓이는 것
- 트랩 진입 코드가 레지스터 하나를 빠뜨려 가끔만 깨지는 것. 재현이 어려워 학습을 방해한다
- 분리 크레이트를 위해 커널 코드에 쓸모없는 추상화 계층을 만드는 것

## 제약

- 개발 환경: Apple Silicon macOS(호스트 `aarch64-apple-darwin`), Rust stable, `qemu-system-riscv64` 11.0.2
- QEMU: `-machine virt -bios none -smp 4 -m 128M`, CPU는 기본값(`rv64`)
- 외부 크레이트 없음(D15). CSR 접근은 인라인 어셈블리로 직접 작성한다
- 1단계가 남기는 것을 전제로 한다. `kmain()`이 S 모드에서 코어 4개로 돌고, `SpinLock`과 `println!`이 있고, `medeleg`/`mideleg`가 `0xffff`로 모든 예외·인터럽트를 S 모드에 위임하고, PMP가 열려 있고, `tp`에 코어 번호가 있다

## 미리 확인한 사실

| 사실 | 확인 방법 |
|---|---|
| 기본 CPU가 Sstc 확장을 지원한다 | `qemu-system-riscv64 -machine virt,dumpdtb=virt.dtb -bios none -smp 4`로 뽑은 디바이스 트리의 `riscv,isa-extensions`에 `"sstc"`가 있다 |
| 타이머 주파수는 10MHz다 | 같은 디바이스 트리의 `timebase-frequency = <0x989680>` (10,000,000) |
| CLINT는 `0x2000000`에 있다 | 같은 디바이스 트리의 `clint@2000000` |

## 타이머 인터럽트가 S 모드에 닿는 길

RISC-V의 원래 타이머는 CLINT라는 장치의 `mtimecmp` 레지스터다. 현재 시각(`mtime`)이 이 값을 넘으면 **M 모드** 타이머 인터럽트가 난다. 이 인터럽트는 S 모드에 위임할 수 없다. 그래서 S 모드 커널이 타이머를 받으려면 누군가 다리를 놓아야 한다. 방법은 셋이다.

| 방식 | 동작 | 누가 쓰나 | 장점 | 단점 |
|---|---|---|---|---|
| **A. Sstc 확장** | S 모드가 `stimecmp` CSR에 직접 다음 시각을 쓴다. 시각이 되면 S 모드 타이머 인터럽트가 바로 난다 | 현재 xv6-riscv, Linux(하드웨어가 지원할 때) | M 모드 코드가 초기 설정 몇 줄뿐이다. 트랩 경로가 S 모드 하나다 | Sstc가 없는 오래된 보드에서는 못 쓴다 |
| B. M 모드가 받아서 넘겨줌 | M 모드 트랩 처리기가 타이머를 받아 `mtimecmp`를 다시 설정하고, S 모드 소프트웨어 인터럽트를 일으켜 S 모드에 알린다 | 예전 xv6-riscv(`timervec`) | M 모드 트랩 처리를 직접 겪는다. 모든 하드웨어에서 동작한다 | 트랩 처리기를 M 모드용, S 모드용 두 벌 만든다. 타이머가 "소프트웨어 인터럽트"로 둔갑해 처음 읽는 사람이 헷갈린다 |
| C. 작은 SBI 직접 구현 | S 모드가 `ecall`로 M 모드에 "이 시각에 깨워 달라"고 부탁한다. M 모드가 `mtimecmp`를 설정하고, 인터럽트가 나면 S 모드 타이머 인터럽트 대기 비트를 세운다 | Linux(Sstc가 없을 때 OpenSBI의 `sbi_set_timer`를 통해) | 실제 보드에서 Linux가 쓰는 계층 구조(커널 → 펌웨어)를 그대로 본다 | B보다 코드가 더 많다. 1단계가 `ecall`(S 모드)을 S 모드에 위임해 두었으므로 위임 설정부터 바꿔야 한다 |

**추천: A** (Q21에서 확정). xv6와 Linux가 지금 쓰는 방식이고, 이번 단계의 학습 대상인 S 모드 트랩 경로에 집중할 수 있다. B와 C를 고르지 않아 M 모드 트랩 처리를 직접 겪는 기회는 줄어든다. 이 대가는 학습 노트에서 B와 C의 동작을 설명하는 것으로 보완한다.

A를 쓰려면 M 모드의 `start()`가 코어마다 두 가지를 더 설정한다.

| 대상 | 값 | 이유 |
|---|---|---|
| `menvcfg` | 비트 63(STCE)을 1로 | S 모드가 `stimecmp`를 쓸 수 있게 한다. 이 비트가 0이면 `stimecmp` 접근이 예외가 된다 |
| `mcounteren` | 비트 1(TM)을 1로 | S 모드가 `rdtime`으로 현재 시각을 읽을 수 있게 한다 |

`mideleg`는 1단계에서 이미 `0xffff`라서 S 모드 타이머 인터럽트(5번)는 S 모드로 간다.

## 검토한 방식

### 트랩 입구를 몇 개 둘 것인가

| 방식 | 장점 | 단점 |
|---|---|---|
| **A. 입구 하나(`stvec` direct 모드), 원인은 `scause`로 가름** | 레지스터 저장 코드가 한 벌이다. xv6와 Linux 모두 이 방식이다 | 원인 판별을 소프트웨어가 한다 |
| B. 인터럽트마다 다른 입구(vectored 모드) | 인터럽트 종류별로 바로 점프한다 | 입구마다 저장 코드가 필요하거나 결국 공통 코드로 모인다. 지금은 인터럽트가 타이머 하나뿐이다 |

**선택: A.**

### 무엇을 어디에 저장할 것인가

트랩은 아무 명령어 사이에서나 끼어든다. 처리기가 레지스터를 하나라도 바꿔 놓으면 원래 코드는 영문도 모르고 틀린 값으로 계속 돈다. 그래서 진입하자마자 레지스터를 저장한다.

| 방식 | 장점 | 단점 |
|---|---|---|
| A. 호출자 저장 레지스터만 스택에 (16개) | 가장 짧다. Rust 함수가 나머지(`s0`~`s11`)는 알아서 보존한다 | 패닉 때 레지스터 전체를 보여 줄 수 없다. 5단계에서 사용자 모드 트랩을 넣을 때 다시 짜야 한다 |
| B. 모든 범용 레지스터를 스택에, CSR은 Rust 지역 변수에 (xv6 `kernelvec`) | xv6와 1:1로 비교된다 | 저장 내용이 어셈블리 순서로만 정의되어 Rust에서 구조로 읽을 수 없다 |
| **C. 범용 레지스터 31개와 `sepc`, `sstatus`, `stval`, `scause`를 `#[repr(C)]` 구조체(`TrapFrame`)로 스택에 (Linux `pt_regs`)** | Rust 처리기가 `&mut TrapFrame`으로 받아 읽고 고칠 수 있다(`ebreak` 뒤 `sepc` 이동, 패닉 때 레지스터 출력). 5단계의 사용자 모드 트랩과 문맥 교환이 같은 구조를 이어 쓴다 | A보다 저장·복원이 길다. 구조체 필드 순서와 어셈블리 오프셋이 어긋나면 안 된다 |

**선택: C.** 레지스터 저장 비용은 이 단계에서 문제가 되지 않고, 프레임을 Rust 타입으로 다루는 이점이 크다. 오프셋 불일치 위험은 `core::mem::offset_of!`로 컴파일 시간에 검사해 막는다.

### 스핀락이 인터럽트를 끄는 방식

| 방식 | 장점 | 단점 |
|---|---|---|
| **A. `lock()`이 항상 인터럽트를 끈다. 중첩 횟수를 코어별로 세어, 가장 바깥 락을 놓을 때만 원래 상태로 되돌린다 (xv6 `push_off`/`pop_off`)** | 실수로 교착을 만들 수 없다. 규칙이 하나다 | 인터럽트와 무관한 락도 인터럽트를 끈다 |
| B. 끄는 락과 안 끄는 락을 따로 두고 쓰는 쪽이 고른다 (Linux `spin_lock` / `spin_lock_irqsave`) | 인터럽트 지연을 최소화한다 | 고르는 규칙을 하나라도 틀리면 가끔만 교착된다 |

**선택: A.** 지금 커널은 작아서 인터럽트 지연이 문제가 되지 않는다. Linux가 왜 B를 택했는지(수천 개의 락, 인터럽트 지연이 곧 응답 시간)는 학습 노트에서 다룬다.

### 틱을 어디에 셀 것인가

| 방식 | 장점 | 단점 |
|---|---|---|
| **A. 코어별 카운터. 각 코어의 처리기는 자기 카운터만 고친다** | 공유가 없으니 락도 필요 없다 | 전체 시간을 하나로 보려면 따로 모아야 한다 |
| B. 전역 카운터 하나를 락으로 보호, 0번 코어만 증가 (xv6 `ticks`) | 시간이 하나로 정의된다 | 이번 단계에서 전역 시간을 쓰는 곳이 없다 |

**선택: A.** 목표 출력이 "코어마다" 틱이다. 공유를 없애는 것이 락보다 앞서는 해법임을 보인다. 전역 시간은 5단계에서 `sleep` 같은 기능이 필요할 때 넣는다.

## 설계

### 트랩 흐름

```
kmain() 실행 중 (S 모드, sstatus.SIE = 1)
  → 하드웨어: stimecmp <= time 이 되면 S 모드 타이머 인터럽트
       sepc ← 끼어든 명령어 주소, scause ← 0x8000_0000_0000_0005
       sstatus.SPIE ← SIE, SIE ← 0  (처리 중에는 인터럽트가 다시 들어오지 않는다)
       pc ← stvec
  → trap_entry                (어셈블리)
       sp를 TrapFrame 크기(288바이트)만큼 내리고 레지스터 31개와 CSR 4개 저장
       a0 = sp 로 trap_handler 호출
  → trap_handler(&mut TrapFrame)   (Rust)
       scause를 Trap으로 해석해 분기
         타이머     → stimecmp ← time + 간격, 코어별 틱 +1, 10틱마다 출력
         ebreak     → 출력, sepc를 명령어 길이(2 또는 4바이트)만큼 이동
         그 밖      → TrapFrame 내용과 함께 패닉
  → trap_entry 나머지
       sepc, sstatus를 프레임에서 복원 (처리기가 고친 값이 반영된다)
       레지스터 복원, sp 되돌림
  → sret: pc ← sepc, SIE ← SPIE
```

인터럽트는 `sepc`를 그대로 두고 돌아가 끼어든 명령어부터 다시 실행한다. 예외는 그 명령어가 원인이므로 그대로 돌아가면 같은 예외가 반복된다. 그래서 `ebreak`는 `sepc`를 다음 명령어로 옮긴다. 이 차이를 학습 노트에서 다룬다.

### `TrapFrame` 배치

Linux `pt_regs`와 같은 순서다. 0번 칸은 항상 0인 `x0` 대신 `sepc`를 둔다.

| 칸 | 오프셋 | 내용 |
|---|---|---|
| 0 | 0 | `sepc` |
| 1~31 | 8~248 | `x1`(`ra`) ~ `x31`(`t6`). 칸 번호가 레지스터 번호와 같다 |
| 32 | 256 | `sstatus` |
| 33 | 264 | `stval` |
| 34 | 272 | `scause` |
| (여백) | 280 | 16바이트 정렬용. 전체 288바이트 |

- `sp` 칸에는 트랩 직전의 `sp`(프레임을 내리기 전 값)를 기록한다. 복원은 `sp`를 288만큼 올리는 것으로 한다.
- 커널 안 트랩만 다루므로 같은 코어 스택(1단계의 코어별 부트 스택 64KiB)에 프레임을 쌓는다. `tp`는 커널이 바꾸지 않으므로 그대로 둔다.

### `scause` 해석과 분기

`scause`의 최상위 비트가 1이면 인터럽트, 0이면 예외다. 나머지 비트가 번호다. 이 해석은 하드웨어와 무관하므로 분리 크레이트에 둔다.

```rust
// klib (분리 크레이트)
pub enum Trap {
    Interrupt(Interrupt),   // SupervisorSoftware, SupervisorTimer, SupervisorExternal, Unknown(usize)
    Exception(Exception),   // IllegalInstruction, Breakpoint, LoadPageFault, ... , Unknown(usize)
}
impl Trap {
    pub fn from_scause(scause: usize) -> Trap;
}
```

커널의 `trap_handler`는 `match`로 분기한다. Linux는 예외 번호로 인덱싱하는 함수 표(`excp_vect_table`)를 쓴다. `match`는 같은 일을 하고, 처리하지 않은 경우를 컴파일러가 알려 준다.

### 타이머

- 간격은 1,000,000 사이클(10MHz에서 0.1초)로 xv6와 같다. 10틱마다 한 줄 출력하므로 코어마다 1초에 한 줄이다.
- `kmain()`에서 코어마다: `stvec` 설정 → 첫 `stimecmp` 기록 → `sie.STIE` 켬 → `sstatus.SIE` 켬 → `wfi` 루프. 첫 시각을 쓰기 전에 인터럽트를 켜면 초깃값 때문에 곧바로 인터럽트가 날 수 있으므로 순서를 지킨다.
- 처리기는 출력보다 먼저 다음 `stimecmp`를 쓴다. `stimecmp`를 갱신해야 인터럽트 대기 상태가 풀린다.

### 코어별 상태

```rust
// 커널 src/cpu.rs
struct Cpu {
    intr: IntrNest,   // 인터럽트 끄기 중첩 횟수와 바깥 상태 (klib)
    ticks: u64,       // 이 코어가 받은 타이머 인터럽트 수
}
static CPUS: [PerHart<Cpu>; MAX_HARTS];
```

- `tp`의 코어 번호로 자기 칸을 찾는다. xv6의 `cpus[cpuid()]`와 같다.
- 자기 칸은 자기 코어만, 그것도 인터럽트가 꺼진 상태에서만 고친다. 그래서 락 없이 `UnsafeCell`로 둔다. 이 전제를 `PerHart` 타입의 접근 함수 하나에 모아 둔다.
- Linux는 다르다. 커널 안에서 `tp`가 지금 실행 중인 태스크(`task_struct`)를 가리키고, 코어 번호는 그 태스크 정보에서 읽는다. 코어별 데이터는 코어마다 따로 복사된 메모리 영역(per-cpu 영역)에 둔다. 우리는 5단계에서 태스크가 생길 때 이 차이를 다시 본다.

### 인터럽트를 끄는 스핀락

```
lock():   was_on = sstatus.SIE; SIE ← 0; cpu.intr.push(was_on); 원자적 획득
unlock(): 원자적 해제; if cpu.intr.pop() { SIE ← 1 }
```

- 끄기를 획득보다 먼저 한다. 반대로 하면 획득 직후, 끄기 직전에 인터럽트가 끼어들 수 있다.
- `IntrNest`(중첩 횟수, 가장 바깥에서 인터럽트가 켜져 있었는지)는 하드웨어와 무관한 상태 기계라 분리 크레이트에 둔다. 횟수가 0인데 `pop`하면 패닉한다.
- 처리기 안에서는 하드웨어가 이미 `SIE`를 꺼 두었으므로 `push`가 "원래 꺼져 있었음"을 기록하고, `pop`이 인터럽트를 켜지 않는다. 처리 도중에 인터럽트가 켜지는 일이 없다.
- 패닉 핸들러는 맨 먼저 인터럽트를 끈다. 패닉 메시지가 틱 출력과 섞이거나 처리기가 다시 들어오지 않게 한다.

### 분리 크레이트 시작

| 항목 | 내용 |
|---|---|
| 위치 | 저장소의 `klib/`. 루트 `Cargo.toml`을 워크스페이스로 바꾸고 커널이 경로 의존성으로 쓴다 |
| 형태 | `#![no_std]` 라이브러리. 테스트에서만 `std`를 쓴다 |
| 실행 | `.cargo/config.toml`의 기본 타깃이 RISC-V라서 그냥 `cargo test`는 실행 파일을 Mac에서 돌릴 수 없다. 별칭 `cargo htest`(= `cargo test -p klib --target aarch64-apple-darwin`)를 둔다 |
| 이번에 옮기는 것 | `Trap::from_scause`, 명령어 길이 판별(`insn_len`: 첫 16비트의 하위 2비트가 `0b11`이면 4바이트, 아니면 압축 명령어 2바이트), `IntrNest`, 원자적 스핀락 본체(Q22) |
| 커널에 남는 것 | CSR 읽기·쓰기, `trap_entry` 어셈블리, `TrapFrame`, 인터럽트 끄기를 붙인 커널용 `SpinLock` |

크레이트 이름과 경계를 정하는 원칙은 하나다. CSR이나 메모리 주소를 직접 만지면 커널, 아니면 `klib`. 커널 쪽 코드를 테스트하려고 하드웨어를 흉내 내는 계층은 만들지 않는다.

Q22를 추천대로 하면 원자적 획득·해제 부분이 `klib::RawSpinLock<T>`로 가고, 커널의 `SpinLock<T>`은 그것에 인터럽트 끄기를 감싼다. Mac에서 실제 스레드 여러 개로 같은 카운터를 수백만 번 올려 잃어버린 증가가 없는지 확인한다. Apple Silicon은 ARM이라 메모리 순서 규칙이 RISC-V처럼 약하다. 메모리 순서(`Acquire`/`Release`)를 잘못 고르면 QEMU보다 Mac에서 먼저 드러날 가능성이 높다.

## 완료 확인

- `cargo run`에서 `[S] hart 0 틱 10`부터 `[S] hart 3 틱 10`까지, 이어서 `틱 20`이 코어마다 나온다. 줄이 섞이지 않는다.
- `-d int`로 받은 QEMU 로그에 S 모드 타이머 인터럽트(원인 5)만 있고 M 모드 타이머 인터럽트(원인 7)는 없다. 타이머가 M 모드를 거치지 않음을 보인다.
- 임시로 `kmain()`에서 M 모드 CSR을 읽으면 `IllegalInstruction`, `sepc`, `stval`이 담긴 패닉 메시지가 나온다(1단계에서는 로그로만 볼 수 있었다).
- 임시로 `kmain()`에 `ebreak`를 넣으면 처리 메시지가 나온 뒤 틱 출력이 계속된다.
- 임시로 스핀락의 인터럽트 끄기를 빼고 `kmain()`이 쉬지 않고 출력하게 하면, 어떤 코어의 출력이 멈추는 교착이 나올 수 있다. 결과를 학습 노트에 인용한다. 되돌리면 멈추지 않는다.
- `cargo htest`가 통과한다.
- `SMP=1`에서도 동작하고, 디버그와 릴리스 빌드 모두에서 위가 성립한다.
