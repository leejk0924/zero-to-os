# 1단계 설계: 부팅 → 여러 코어 시작 → Rust 커널 진입 → 글자 출력

- 작성일: 2026-11-14, 수정일: 2026-11-19 (코어 1개 → 코어 4개)
- 프로젝트 전체의 결정과 이유는 `docs/decision/decisions.md`에 있다. 이 문서는 1단계에만 해당하는 내용을 다룬다.

## 의도

전원이 켜진 순간부터 커널이 문장을 출력할 때까지를 직접 만든다. 여러 코어가 동시에 깨어나는 상황을 처음부터 다뤄, 동시성의 첫 문제(공유 자원, 락)를 가장 작은 예제로 겪는다.

## 목표

- `cargo run` 한 번으로 QEMU가 뜨고, 코어 4개가 각자 S 모드에서 `[S] hart N 시작`을 출력한다.
- 출력되는 줄이 서로 섞이지 않는다.
- 전원 직후 첫 명령어부터 출력까지 실행되는 코드가 모두 이 저장소에 있다.

## 이번 단계에서 하지 않는 것

- 인터럽트·트랩 처리, 타이머 (2단계)
- 메모리 할당기, 가상 메모리
- 키보드 입력, 그래픽 화면 출력
- 실제 보드에서 실행

## 피해야 할 것

- 동작은 하지만 사용자가 이해하지 못한 코드가 쌓이는 것
- 하드웨어를 가려 버리는 외부 크레이트에 의존하는 것

## 제약

- 개발 환경: Apple Silicon macOS, Rust stable, `qemu-system-riscv64` 11.0.2
- 외부 크레이트 없음. CSR 접근은 인라인 어셈블리로 직접 작성한다.
- 빌드 도구는 `cargo`만 쓴다.

## 검토한 방식

### 다른 코어를 언제 깨울 것인가

펌웨어 없이 부팅하면 모든 코어가 동시에 `0x80000000`에서 실행을 시작한다.

| 방식 | 장점 | 단점 |
|---|---|---|
| **A. 0번 코어가 초기화를 마칠 때까지 나머지는 어셈블리에서 대기** | 초기화 중에는 코어 하나만 Rust 코드를 실행하므로 `.bss` 초기화와 UART 설정이 안전하다 | 대기 신호용 변수를 `.bss` 밖에 둬야 한다 |
| B. 모든 코어가 곧바로 Rust로 진입 (xv6 방식) | 코드가 짧다 | `.bss`를 지우지 않고 QEMU가 메모리를 0으로 채워 준다는 사실에 기대야 한다 |

**선택: A.** 실제 하드웨어는 메모리를 0으로 채워 주지 않는다. 대기 신호를 `.bss` 밖에 둬야 하는 이유 자체가 배울 거리다.

### 출력이 섞이지 않게 하는 방법

| 방식 | 장점 | 단점 |
|---|---|---|
| **A. UART를 스핀락으로 보호** | 이후 모든 공유 자료구조에 쓸 락을 지금 만든다 | 패닉 때 락을 쥔 채 멈추면 메시지가 안 나올 수 있어 따로 처리해야 한다 |
| B. 코어가 순서대로 하나씩 출력 | 락이 필요 없다 | 동시 실행을 피하는 것이라 배울 것이 없다 |

**선택: A.**

## 설계

### 실행 환경

- 타깃: `riscv64gc-unknown-none-elf`
- QEMU: `-machine virt -bios none -smp 4 -m 128M -nographic`

### 부팅 흐름

```
QEMU 리셋 벡터(0x1000) — 모든 코어가 동시에
  → 0x80000000 `_start`   (어셈블리, M 모드)
       코어 번호(mhartid)로 자기 스택을 잡는다
       0번 코어: .bss를 0으로 채우고 진행
       나머지 코어: BOOT_READY가 1이 될 때까지 대기
  → `start(hartid)`       (Rust, M 모드)
       0번 코어: UART 초기화, 메시지 출력, BOOT_READY를 1로
       모든 코어: S 모드로 내려갈 준비, 코어 번호를 tp 레지스터에 저장
  → `mret`
  → `kmain()`             (Rust, S 모드)
       `[S] hart N 시작` 출력, 대기 루프
```

`start()`가 코어마다 M 모드에서 하는 일:

1. `mstatus`의 이전 권한 필드를 S 모드로 설정
2. `mepc`에 `kmain` 주소 기록
3. `satp`를 0으로 두어 페이징 끔
4. `medeleg`, `mideleg`로 예외·인터럽트를 S 모드에 위임
5. PMP를 열어 S 모드가 전체 메모리에 접근하도록 허용
6. 코어 번호를 `tp`에 저장 (S 모드에서는 `mhartid`를 읽을 수 없다)
7. `mret`로 S 모드 진입

### 구성 요소

| 파일 | 역할 |
|---|---|
| `src/entry.S` | `_start`: 코어별 스택 설정, `.bss` 초기화, 대기, Rust로 점프 |
| `kernel.ld` | 링커 스크립트: 시작 주소 `0x80000000`, 진입 코드를 맨 앞에 배치, 코어별 부트 스택 영역 |
| `src/main.rs` | `start()`, `kmain()`, 패닉 핸들러 |
| `src/uart.rs` | NS16550A UART(`0x10000000`) 출력, `print!`/`println!` |
| `src/spinlock.rs` | `SpinLock<T>` |
| `.cargo/config.toml` | 기본 타깃, `cargo run` 시 QEMU 실행 |
| `build.rs` | 링커 스크립트 지정 |
| `rust-toolchain.toml` | stable 채널과 타깃 고정 |
| `scripts/check.sh` | QEMU를 잠깐 띄워 출력을 검사 |

### 그 밖의 선택

- 코어는 최대 4개까지 지원한다. 그보다 번호가 큰 코어는 `_start`에서 멈춘다.
- 스핀락은 인터럽트를 끄지 않는다. 1단계에는 인터럽트가 없다. 2단계에서 추가한다.
- 패닉 핸들러는 락을 거치지 않고 UART에 직접 쓴다. 패닉이 난 코어가 락을 쥐고 있어도 메시지가 나와야 한다.

## 완료 확인

- `cargo run` 실행 시 `[S] hart 0 시작`부터 `[S] hart 3 시작`까지 네 줄이 순서와 무관하게, 섞이지 않고 출력된다.
- S 모드임을 확인한다: S 모드에서 M 모드 전용 CSR을 읽으면 예외가 나는 것을 QEMU 로그(`-d int`)로 본다. 이 환경에는 GDB가 없고 QEMU 모니터는 권한 레벨을 보여 주지 않는다.
- 락을 잠시 빼면 출력이 섞일 수 있음을 실험으로 본다.
- 일부러 `panic!`을 넣으면 패닉 메시지가 출력된다.
- 디버그와 릴리스 빌드 모두에서 위가 성립한다.

## 만드는 사람에게 맡기는 것

- 출력 문구의 세부, 함수·심볼 이름 (계획에서 정한 것 제외)
- 스핀락의 대기 방식 세부
