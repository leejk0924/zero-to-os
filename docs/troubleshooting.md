# 문제 해결 기록

겪은 문제를 증상, 원인, 해결 순서로 적는다. 같은 문제를 다시 만났을 때 증상으로 찾을 수 있게 증상은 실제 오류 문구로 쓴다.

## 개발 환경

### `gh` 명령이 `HTTP 401: Bad credentials`로 실패한다

- 원인: 셸의 `GITHUB_TOKEN` 환경 변수에 만료된 토큰이 들어 있고, `gh`가 키체인 로그인보다 이 변수를 먼저 쓴다.
- 해결: `env -u GITHUB_TOKEN gh ...`로 실행한다.

### QEMU를 일정 시간만 실행하고 싶은데 `timeout` 명령이 없다

- 원인: macOS에는 `timeout`이 기본으로 없다.
- 해결: 백그라운드로 띄우고 `sleep` 뒤 `kill`한다. `scripts/check.sh`가 이 방식을 쓴다.

### 지금 코드가 어느 권한 레벨(M/S)에서 도는지 확인할 방법이 없다

- 원인: 이 Mac에는 RISC-V용 GDB가 없고, QEMU 모니터의 `info registers`는 권한 레벨을 보여 주지 않는다. RISC-V에는 자기 권한 레벨을 읽는 명령도 없다.
- 해결: M 모드 전용 CSR(`mstatus` 등)을 읽어 본다. S 모드라면 예외가 나고, QEMU를 `-d int -D <로그 파일>`로 실행하면 로그에 `illegal_instruction`이 남는다.

## 빌드

### `kmain as usize`에서 `function_casts_as_integer` 경고가 난다

- 원인: 함수를 바로 정수로 바꾸는 것을 Rust가 경고한다.
- 해결: `kmain as *const ()`로 포인터로 바꿔 넘긴다. `asm!`의 `in(reg)`는 포인터를 받는다.

## 실행

### S 모드에서 예외가 난 뒤 QEMU `-d int` 로그에 `desc=fault_fetch`(cause 1, `epc:0x0`)가 끝없이 쌓인다

- 원인: `medeleg`로 예외를 S 모드에 위임했지만 `stvec`이 0이다. 예외가 나면 주소 0으로 뛰고, 0에는 메모리가 없어 명령 가져오기에서 다시 예외가 난다. 2초에 약 79만 줄이 쌓인다.
- 해결: 1단계에서는 그대로 둔다(트랩 처리기가 없다). 2단계에서 `stvec`에 트랩 처리기를 두면 사라진다. 로그를 볼 때는 `grep -m1`로 첫 줄만 본다.

### 일부러 넣은 `panic!`의 메시지가 출력되지 않는다

- 원인: 패닉한 코어가 UART 락을 쥔 채였는데 패닉 처리기가 `println!`(락을 기다림)을 썼다. 락이 영원히 풀리지 않는다.
- 해결: 패닉 처리기는 `uart::print_panic`을 쓴다. 락을 정해진 횟수만 시도하고 못 얻으면 락 없이 출력한다(D24).

### 모든 코어가 동시에 패닉하면 `scripts/check.sh "커널 패닉: "`가 가끔 실패한다

- 증상: 출력이 `[S] hart 0 커널 패닉: 시작`처럼 섞인다.
- 원인: 락 없는 패닉 출력끼리, 또는 패닉 출력과 다른 코어의 `println!`이 바이트 단위로 섞였다.
- 해결: 첫 코어만 출력하고(`PANICKING`), 출력 전에 UART 락을 시도해 진행 중인 줄이 끝나길 기다린다(D24). 고친 뒤 디버그·릴리스 각 10/10 통과.
