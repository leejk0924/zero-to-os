# ADR 0001: 코어별 스택, 부팅 대기, UART 출력

- 상태: 채택
- 날짜: 2026-11-19
- 이슈: #1 태스크 2
- 계획: `docs/decision/plans/2026-11-14-boot-hello.md`

## 맥락

태스크 1의 `_start`는 스택 없이 글자 하나만 썼다. Rust 코드를 부르려면 코어마다 스택이 있어야 하고, `.bss`를 0으로 채워야 하며, 초기화가 끝나기 전에 다른 코어가 Rust로 들어오지 않아야 한다. 계획은 순서와 인터페이스를 정했지만 대기 신호의 메모리 순서, `.bss`를 지우는 단위, `print!` 매크로의 구조는 정하지 않았다.

## 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| `_start` 순서(번호 확인 → 스택 → 0번만 `.bss` 지우기 → 나머지 대기 → `call start`), 스택 64KiB × 4, `BOOT_READY`를 `.data`에 두기 | 계획대로 | |
| UART 레지스터 값, `volatile` 접근, `start()`와 패닉 핸들러의 동작 | 계획대로 | |
| 대기 루프가 `BOOT_READY`를 본 뒤 `fence r, rw`를 둔다 | Rust 쪽 `Ordering::Release` 저장과 짝을 이루는 획득(acquire)이다. 이것이 없으면 RISC-V의 약한 메모리 모델에서 0번 코어의 초기화 결과보다 신호가 먼저 보일 수 있다 | 장벽 없이 읽기만 하기(QEMU에서는 보통 동작하지만 규칙상 보장이 없다) |
| 코어 번호를 처음부터 `a0`에 읽어 두고 그대로 `start`의 인자로 넘긴다 | 호출 규약상 첫 인자가 `a0`라 옮기거나 저장할 필요가 없고, 대기 루프는 `t` 레지스터만 쓴다 | 다른 레지스터에 두었다가 호출 직전 `a0`로 옮기기 |
| `.bss`를 `sd`로 8바이트씩 지운다 | 링커 스크립트가 `__bss_start`, `__bss_end`를 8바이트로 맞춰 두어 넘칠 일이 없고, 바이트 단위보다 반복이 8배 적다 | `sb`로 1바이트씩 |
| `print!`/`println!`은 `#[macro_export]`로 정의하고 `$crate::uart::_print(format_args!(..))`를 부른다. `main.rs`는 `#[macro_use] mod uart;`로 가져온다 | `std`의 `println!`과 같은 구조라 읽기 쉽고, 서식 처리는 `core::fmt::Write`의 기본 구현(`write_fmt`)에 맡긴다. `_print`가 한 곳이라 태스크 3에서 락을 여기에만 넣으면 된다 | 매크로마다 `Uart` 값을 만들어 직접 `write!` 하기(락을 넣을 곳이 흩어진다) |
| `_print`는 `write_fmt`의 `fmt::Result`를 버린다 | `write_str`이 항상 `Ok`를 돌려주므로 실패할 경로가 없다 | 결과를 `unwrap`하기(실패할 수 없는 경로에 패닉 코드만 더한다. 패닉 핸들러도 이 함수를 쓴다) |
| 줄바꿈은 `\n`만 쓴다 | `std`, xv6와 같다. QEMU 터미널에서 계단 모양으로 밀리는지는 태스크 4의 `cargo run`에서 눈으로 확인한다(미확인) | `\r\n`으로 바꿔 쓰기 |

## 결과

- 4번 이상 코어는 `_start`의 `park` 루프에 머물고, 0~3번 코어는 모두 `start()`의 `wfi` 루프에 있다. QEMU 모니터 `info registers -a`에서 네 코어의 `pc`가 같은 `start` 안 주소, `sp`가 64KiB 간격(`0x80011ef0`, `0x80021ef0`, ...)으로 확인됐다.
- 지금 `_print`에는 락이 없다. 태스크 3이 `SpinLock`을 넣기 전까지 0번 코어 외의 코어에서 `println!`을 부르면 글자가 섞인다.
- 패닉 핸들러도 `_print`를 쓴다. 태스크 3에서 락을 넣을 때 패닉 경로는 락을 거치지 않게 해야 한다(설계 문서 요구).
