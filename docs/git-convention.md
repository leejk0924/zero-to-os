# 깃 컨벤션

이슈 하나에 PR 여러 개를 쌓아 작업한다. PR이 크면 이해하기 어려우므로, PR 하나는 **최소한의 추상적인 기능 단위** 하나만 담는다.

## 이슈, PR, 태스크

- 로드맵의 단계 하나 = 이슈 하나 (`docs/spec.md`의 이슈 열).
- 계획의 태스크 하나 = 브랜치 하나 = PR 하나. 그래서 계획을 쓸 때부터 태스크를 "PR로 읽기 좋은 크기의 기능 하나"로 자른다.
- 한 이슈의 PR들은 `gh stack`으로 차례대로 쌓는다. 뒤 태스크의 PR은 앞 태스크의 PR 위에 올라간다.
- 문서만 바꾸는 `Docs` 커밋은 예외로, 브랜치와 PR 없이 `main`에 바로 커밋하고 push한다.
- PR 본문에는 `Refs #<이슈>`를 적는다. 이슈를 닫는 것은 마지막 PR(또는 마무리 단계)에서 `Closes #<이슈>`로 한다.

## 커밋 유형

| 커밋 유형 | 의미 |
|---|---|
| `Feat` | 새로운 기능 추가 |
| `Fix` | 버그 수정 |
| `Docs` | 문서 수정 |
| `Style` | 코드 formatting, 세미콜론 누락 등 코드 자체의 변경이 없는 경우 |
| `Refactor` | 코드 리팩토링 |
| `Test` | 테스트 코드, 리팩토링 테스트 코드 추가 |
| `Chore` | 패키지 매니저 수정, 그 외 기타 수정(예: `.gitignore`) |
| `Design` | CSS 등 사용자 UI 디자인 변경 |
| `Comment` | 필요한 주석 추가 및 변경 |
| `Rename` | 파일 또는 폴더 이름을 수정하거나 옮기는 작업만인 경우 |
| `Remove` | 파일을 삭제하는 작업만 수행한 경우 |
| `!BREAKING CHANGE` | 큰 API 변경의 경우 |
| `!HOTFIX` | 급하게 치명적인 버그를 고쳐야 하는 경우 |

## 커밋 메시지

```
<유형>: <한국어 요약>

<필요하면 본문: 무엇을, 왜>
```

- 예: `Feat: 코어마다 어셈블리에서 글자 출력`, `Fix: check.sh가 QEMU 진단 출력을 시리얼 출력으로 섞는 문제`
- 이슈 번호는 커밋에 붙이지 않는다. 브랜치 이름과 PR 본문으로 연결한다.

## 브랜치

```
<유형>/<이슈 번호>-<기능 단위>
```

- 예: `Feat/1-boot-skeleton`, `Feat/1-spinlock`, `Fix/2-timer-tick`
- 기능 단위는 영어 소문자 kebab-case로 짧게 쓴다.
- `!` 유형은 브랜치 이름에 그대로 쓸 수 없어(공백 불가, 셸 히스토리 확장과 충돌) 접두어만 바꾼다: `!HOTFIX` → `Hotfix/`, `!BREAKING CHANGE` → `Breaking/`. 커밋 메시지에는 `!HOTFIX: ...`처럼 원래 유형을 쓴다.
- 브랜치의 유형은 그 PR의 주된 변경을 따른다. PR 안의 개별 커밋은 각자 맞는 유형을 쓴다(예: `Feat/` 브랜치 안의 `Fix:` 커밋).

## PR

- 제목은 커밋 메시지 첫 줄과 같은 형식: `<유형>: <한국어 요약>`
- 브랜치 하나에서 PR 하나를 만든다.

## `gh stack` 흐름

```sh
# 이슈의 첫 태스크: main 위에 스택을 시작한다
gh stack init Feat/1-boot-skeleton
# ...구현, 커밋, Codex 검토, 수정...

# 다음 태스크: 스택 위에 브랜치를 더한다
gh stack add Feat/1-uart-println

# 스택의 모든 브랜치를 push하고 PR을 만들거나 갱신한다
gh stack submit

# 스택 상태 확인, main과 동기화
gh stack view
gh stack sync

# 아래 PR부터 차례대로 병합한다
gh stack merge
```

- 아래쪽 PR을 고치면 `gh stack rebase`로 위쪽 브랜치를 다시 올린다.
- PR 생성과 병합은 사용자가 요청할 때 한다.
